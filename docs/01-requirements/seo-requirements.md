# الزامات SEO فنی و محتوایی

**اهمیت: بحرانی برای صفحات عمومی؛ دروازهٔ انتشار اجباری.** هیچ تکنیکی رتبهٔ اول گوگل را تضمین نمی‌کند. معیار ما قابل خزش بودن، صحت سیگنال‌ها، محتوای ارزشمند، عملکرد و اندازه‌گیری واقعی است.

## 1. رندر و دسترس‌پذیری محتوا
- صفحات عمومی با Blade در سمت سرور رندر می‌شوند؛ متن اصلی، عنوان، لینک‌های مهم و breadcrumbs نباید برای ظاهرشدن به JavaScript نیاز داشته باشند.
- تعاملات نقشه/فیلتر می‌توانند به JavaScript سبک Progressive Enhancement نیاز داشته باشند، اما لینک‌ها و اطلاعات پایه باید HTML معنایی داشته باشند.
- خطای سرور یا draft نباید ناخواسته HTML قابل ایندکس با دادهٔ ناقص ارائه کند.

## 2. معماری URL و چندزبانه
- URLهای عمومی فارسی با `/fa/` و انگلیسی با `/en/` آغاز می‌شوند.
- هر زبان canonical خود را دارد؛ نسخهٔ فارسی نباید canonical نسخهٔ انگلیسی باشد و برعکس.
- `hreflang` برای صفحات واقعاً معادل، به‌شکل متقابل و با کدهای زبان معتبر (`fa-IR` و `en`) ثبت می‌شود.
- URL ریشه در پایلوت به `/fa` هدایت می‌شود؛ پیش از انتشار عمومی، صحت انتخاب این سیاست و رفتار `x-default` بازبینی شود.
- تغییر slug باید redirect پایدار و کنترل‌شده داشته باشد؛ زنجیره و حلقهٔ redirect ممنوع است.

## 3. metadata و social preview
- هر صفحهٔ indexable عنوان و توضیحات منحصربه‌فرد و معنی‌دار دارد.
- canonical، robots، Open Graph و زبان صفحه از منبع واحد ساخته شوند.
- تصویر OG در صورت وجود باید URL عمومی و اندازه/کیفیت مناسب داشته باشد؛ URL ساختگی یا تصویر placeholder در تولید منتشر نشود.
- پیش‌نمایش CMS باید `noindex` باشد و در صورت نیاز پشت احراز هویت قرار گیرد.

## 4. ایندکس‌پذیری و sitemap
- sitemap فقط URLهای canonical، منتشرشده، عمومی و پاسخ‌گوی 200 را شامل می‌شود.
- صفحات شرکت/محصول/دوره تنها وقتی منتشر و قابل ایندکس می‌شوند که محتوای کافی و مجوز انتشار داشته باشند.
- صفحات جست‌وجو، فیلترهای ترکیبی، صفحه‌های داخلی کم‌ارزش و مسیرهای تکراری سیاست مشخص `noindex`/canonical دارند.
- `robots.txt` ابزار کنترل خزش است، نه کنترل امنیت؛ مسیر خصوصی باید با authorization محافظت شود.
- sitemap باید URLهای واقعی و hreflang معادل‌ها را فهرست کند؛ صرف وجود فایل sitemap به معنی ایندکس‌شدن نیست.

## 5. structured data
- برای سازمان، رویداد، مسیر breadcrumb و سایر انواع، از Schema.org فقط در صورت تطبیق کامل با محتوای قابل مشاهده استفاده شود.
- دادهٔ ساختاریافته نباید اطلاعات ساختگی، rating جعلی، قیمت ناموجود یا تاریخ تأییدنشده داشته باشد.
- انواع `Event`, `Organization`, `BreadcrumbList` و در صورت شرایط واقعی `Product` بررسی شوند؛ نوع نهایی وابسته به دادهٔ هر صفحه است.

## 6. سرعت و تجربهٔ کاربر
- HTML کم‌حجم و معنایی؛ CSS و JavaScript محدود؛ تصاویر responsive و دارای ابعاد.
- از تصاویر بزرگ بدون بهینه‌سازی، کتابخانهٔ سنگین برای تعامل ساده و layout shift جلوگیری شود.
- اهداف Core Web Vitals پس از ایجاد نمونهٔ واقعی و اندازه‌گیری موبایل تعریف و سپس با دادهٔ میدانی پایش شوند.
- هر صفحهٔ مهم با دستگاه کم‌قدرت و شبکهٔ کند بازبینی شود.

## 7. کنترل انتشار
- بررسی title/description/canonical/hreflang/robots/status code.
- بررسی HTML اولیه، لینک‌های داخلی، 404، redirectها، sitemap و robots.
- بررسی دادهٔ ساختاریافته با ابزارهای رسمی و گزارش خطاها.
- سنجش عملکرد موبایل و accessibility.
- تأیید اینکه صفحات و داده‌های staging ایندکس نمی‌شوند و محیط production به اشتباه `noindex` نیست.
- پس از انتشار، Search Console، sitemap status، خطاهای crawl، index coverage و عملکرد واقعی پایش شود.
