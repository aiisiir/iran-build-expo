# ADR-0001: استک پایلوت و رندر صفحات عمومی

- **وضعیت:** پذیرفته‌شده برای پایلوت؛ بازبینی در صورت تغییر محدودیت‌ها
- **تاریخ:** 2026-10-27
- **تصمیم‌گیر:** مالک محصول

## زمینه
SEO برای صفحات عمومی اهمیت حیاتی دارد. مالک محصول برای پایلوت یک استک واحد و کم‌پیچیدگی می‌خواهد و می‌تواند در صورت نیاز هاست مناسب تهیه کند. اجرای React جداگانه و backend جداگانه در نسخهٔ اول هزینهٔ استقرار و نگهداری اضافی ایجاد می‌کند.

## تصمیم
از Laravel + Blade استفاده می‌کنیم. صفحات عمومی با HTML سمت سرور رندر می‌شوند. React/Next.js و SPA در محدودهٔ پایلوت نیستند. برای تعاملات مورد نیاز، ابتدا HTML و CSS معنایی و سپس JavaScript محدود به‌صورت progressive enhancement استفاده می‌شود.

## دلیل
- محتوای اصلی و metadata از ابتدا در HTML پاسخ موجود است.
- backend و صفحات در یک پروژه و فرایند استقرار نگهداری می‌شوند.
- با میزبانی متداول PHP سازگارتر است، هرچند نسخه و امکانات واقعی هاست هنوز باید تأیید شوند.
- از نظر SEO، سروری‌بودن رندر مسیر روشنی فراهم می‌کند، اما رتبهٔ گوگل به محتوا، تجربهٔ کاربر، اعتبار، رقابت و عوامل دیگر وابسته است و تضمین نمی‌شود.

## گزینه‌های ردشده برای پایلوت
- **React CSR + Laravel API:** با اولویت SEO و هدف یک استک واحد، پیچیدگی غیرضروری دارد.
- **Next.js + Laravel:** دو runtime و دو لایهٔ استقرار ایجاد می‌کند؛ برای پایلوت توجیه نشده است.
- **Next.js تنها:** گزینهٔ معتبر فنی است، اما فعلاً مالک محصول Laravel + Blade را انتخاب کرده است و مزیت عملی کافی برای تغییر تصمیم نداریم.

## پیامدها
- viewها در Blade نگهداری می‌شوند.
- محتوای عمومی، metadata، canonical، hreflang، sitemap و robots باید در Laravel تولید شوند.
- تعامل نقشهٔ سالن‌ها باید بدون وابسته‌کردن محتوای اصلی به JS طراحی شود.
- نسخهٔ PHP و افزونه‌های لازم باید قبل از انتخاب/تأیید هاست تطبیق داده شوند.
- اگر نیازمندی‌های آینده واقعاً استک را ناکافی کنند، تغییر فقط با ADR جدید و شواهد انجام می‌شود.
